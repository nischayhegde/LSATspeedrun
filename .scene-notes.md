# Notes on the 3D scenes

Companion to `.map-generator-notes.md` and `.map-crossing-notes.md`, which cover
the districts and the crowd. This one covers the surfaces a character or an
object is drawn on: the catalog cards, the portrait, and the wardrobe that has to
reach both.

Everything here was measured on a headless Linux VM whose WebGL is SwiftShader,
at device pixel ratio 1. That matters in one direction and not the other: a
number that says *where* the time goes is trustworthy, because the phases are
timed separately in the same process; a number that says how many milliseconds a
player will wait is not, because software rasterisation and a software pixel
readback are not what a phone or a laptop does. Nobody has measured this on a
real phone, and this file does not pretend to.

# Catalog thumbnails: the shadow map was not the cost

Handed over by the interface pass, which had already fixed the freeze and left
the cost alone. Their finding, restated because it is the reason the numbers
below are per-card rather than per-catalog: the renders were serialised through a
chain of already-resolved promises, which is not a queue — a microtask chain
drains inside a single task — so the browser built eleven scenes and encoded
eleven images without ever yielding and froze the main thread for 1521 ms.
Inserting one real task between renders took the worst freeze to 299 ms.

The open question was the per-card cost: 170-300 ms each, fourteen cards to fill
the Firm catalog, and a 1024 shadow map that looks disproportionate for a
thumbnail 372 CSS pixels wide.

## Where the time goes

`catalog-asset-render.tsx` now publishes a per-card breakdown on
`window.__catalogThumbs` under `import.meta.env.DEV`, and
`tools/light-qa/catalog-thumbs.mjs` scrolls the whole catalog past the
intersection observer and reads it. This was necessary rather than fussy: all
three phases happen inside one synchronous call, so from outside the module the
only observable quantity is the total, and the total cannot tell you what to fix.

Over 35 cards, per card:

| phase | ms |
|---|---|
| build the scene | 19 |
| draw it, shadow map and illustrated pass | 9 |
| get the pixels back out of the canvas | 173 |

So the suspect was innocent. Confirmed directly, three arms in one server
lifetime: 1024 is 200.2 ms a card, 512 is 196.2, 256 is 194.3 — and the *draw*
phase does not move at all (8.5, 8.6, 8.9 ms). Six milliseconds of a two-hundred
millisecond card, for softer contact shadows under every desk in the catalog, is
not a trade worth making. It stays at 1024, and `window.__thumbShadow` is there
so the next reader can check that instead of believing this paragraph.

## What did work

**Read it back instead of drawing it again.** A thumbnail is a pure function of
the asset's type, key and tier and of the resolution it was captured at, all four
of which are in the cache key, so a card drawn in an earlier session is still
correct in this one. `frontend/src/art/thumbnail-store.ts` keeps the encoded blob
in IndexedDB; the card asks the store before it asks the renderer. Measured with
a persistent browser profile, the same catalog twice:

| session | thumbnails drawn | per card | long tasks > 50 ms | worst |
|---|---|---|---|---|
| first | 35 | 201 ms | 33 | 272 ms |
| second | **0** | — | **0** | — |

The cards are pixel-identical to the ones they replace: mean absolute difference
0.000, peak 0, on five cards diffed with `tools/light-qa/diff.py`.

IndexedDB rather than `localStorage` because these are blobs — the whole catalog
is about 3 MB, which would be most of a 5 MB string quota and would have to be
base64'd to get in there at all. Every path in the store fails soft: a blocked
store, a private window, a quota refusal or a browser with no IndexedDB resolves
to a miss, and the render happens as it would have.

**`toBlob` instead of `toDataURL`.** The same encoder, and it does not make the
card arrive sooner — 173 ms against 174 — but it drops the base64 step, which is
98.5 kB a card to 73.9, and it is a real task boundary rather than a microtask.
Worth having on those two grounds; not a fix for the freeze, which the interface
pass had already fixed properly.

Incidentally, the store lookup in front of each render turns out to break the
microtask chain on its own: with the old encoder still selected, the same run
that used to show 6 long tasks and a 1219 ms worst freeze now shows 29 and 301
ms. Two independent fixes for one bug is a good position to be in, but the
scheduling one is the one to keep, because it is the one that does not depend on
a store being present.

## What was measured and rejected

Written down so nobody spends the afternoon on them twice.

| idea | result | why not |
|---|---|---|
| copy into a 2D canvas, encode from that | 170 ms against 174 | the readback is deferred, not avoided — `drawImage` off a WebGL canvas measures as free in isolation and then charges for it at the next snapshot |
| JPEG instead of WebP | 145 ms, a real 25 ms saving | ringing on exactly the ink contours the illustrated pass exists to draw |
| capture at the size the card is shown | 150 ms and 28 kB a card | visibly grainier |

The last one is the interesting one, because it looked like free money. The grid
never shows a card wider than 372 CSS pixels — measured at 414, 1440 and 1920
viewport widths — and the renderer captures 640 and then multiplies by the device
pixel ratio, so a retina laptop reads back 1280 x 768 to fill a 372-pixel slot.
That is a 1.7x oversample at every ratio, and it is doing work: the illustrated
pass bands and inks per-pixel, and the downsample is what smooths it. Captured at
384 the dark wall behind the law library speckles, and it is not the codec —
re-encoded at quality 1.0, at 126 kB instead of 28, the speckle is unchanged.

So the cards are as cheap as they can be made without either hurting the art or
finding a cheaper way out of a WebGL canvas, and the second visit is now free.
`window.__thumbWidth`, `__thumbQuality`, `__thumbShadow` and `__thumbEncode` are
all in the tree, so each of these arms can be taken again in one lifetime.
