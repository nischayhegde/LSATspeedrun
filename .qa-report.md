### F-1 — `office-three.css` and `guided-tour.css` swap places on a client-side walk (benign)

Not a cascade defect, but a real order divergence and the one place the rank mechanism
does not reach. Recording it because it is latent.

On `/office` at 390, cold load ends with:

```
  ... index.css, mobile-office-page.css, <google fonts>, office-three.css, guided-tour.css
```

and the walk from `/cases/<uuid>` ends with:

```
  ... index.css, mobile-office-page.css, <google fonts>, guided-tour.css, office-three.css
```

Both sheets land *after* the static Google-fonts link, i.e. at the very end of `<head>`,
behind everything the inline script and the observer placed. Neither is in the route
stylesheet map for `/office` (which lists only `narrative`, `game-art`, `office-page`
in front of the entry and `mobile-office-page` behind it), so **the rank-based reorder
never sees them** — they are sheets belonging to lazily-imported chunks and their
relative order is simply whichever chunk resolves first. Cold load and walk resolve them
in opposite orders.

**Why it is harmless today, checked rather than assumed:** the two sheets share no class
name at all (0 in common). The only selectors literally present in both are `0%` and `to`,
which live inside their own `@keyframes` blocks and so cannot interact. `office-three.css`
is 3.5 kB / 28 selectors; `guided-tour.css` is 16 kB / 129 selectors. There is no pair of
rules that could decide the same property on the same element, so the swap cannot change
a winner.

**The latent risk:** this pair is ordered by chunk-resolution race, not by the mechanism.
If a future change gives these two sheets (or any other pair of lazy-chunk sheets) an
overlapping selector, the cascade will differ between a cold load and a walk and nothing
on the branch will catch it — `nav-order.mjs` only checks sheets that appear in the route
map, and these do not.

Screenshots at 390 were visually identical and have been deleted; the 6 style and 8 rect
diffs are the live 3D scene (`.world-zone` markers at different camera positions, one
mid-fade at `opacity` 0 vs 1), not styling.

### S4-2 — the "stranded halo" lead: **resolved, not a defect**

Run 1 flagged 3 rings, and a tier-2 census flagged 1, as *stranded* — `TorusGeometry` with
`visible = true` under a `visible = false` ancestor, i.e. lit but unrenderable. The tier-2 one
named its ancestor: `Mesh#1089 skip=false under female-visitor-stylized-counsel#1012`.

**My metric was too broad, and the flag is a false positive.** Three things settle it:

1. **`batchSkip = false` on the flagged mesh.** Every focus halo is created by `attachFocus`
   (`office-three.tsx:773`), which sets `halo.userData.batchSkip = true` on line 785. A torus
   with `batchSkip = false` is therefore *not* a halo — it is ordinary character geometry that
   happens to be a torus (the visitor's hair bun, a bag ring). `stylized-counsel` builds bodies
   from ~58 small parts and some of them are tori.
2. **Every batched character part looks like this by design.** `OfficeCastBatch` sets
   `body.visible = false` on the character root (`office-cast-batch.ts:148`) and leaves the
   whole hierarchy in place, deliberately: *"the focus ring, the earnings pick and the
   plan-view probes all read their world positions — so instead of being kept out of the graph
   they are left in it and hidden."* So **every** part of **every** batched body is
   `visible = true` under a hidden root and drawn from the `InstancedMesh`. That is the
   mechanism working, and my census counted it as breakage.
3. **No halo can land inside a batched body.** All eight `attachFocus` call sites attach to
   room furniture, not to a character rig: `clientStation`, `installation` ×2, `seal`,
   `plaque`, `prop`, `staffFloor`, and `place` — where `place` is the seat *marker*
   (`office-three.tsx:2691` sets `place.userData.staffKey`), not the body sitting in it.
   Furniture is the **room** batcher's territory, and that one *does* honour the flag:
   `if (!object.visible || object.userData.batchSkip) return` (`office-room-batch.ts:265`).
   Halos are also created `visible = false`, so they are excluded twice over.

**Confirmed independently by the prior worker's data.** `.room-evidence/interact-reversed.json`
runs `nobatch → batched → nobatch` and reports `stranded: []` for `batchSkip` objects in **all
three** arms, with 67 objects kept out of batches each time. That is the correctly-scoped
version of my metric, and it is clean. I did not need to re-run it.

**One real asymmetry between the two batchers, worth recording as latent.** The room batcher
honours `userData.batchSkip`; the cast batcher **does not check it at all** — it batches every
non-array-material mesh under a body. Today that is harmless, because halos never sit under a
character. But `attachFocus` documents `batchSkip` as meaning "the static batcher must leave
this alone", and one of the two batchers silently does not implement that contract. If anyone
ever attaches a halo, or any animated-material part, to a staff rig, it will be folded into a
batch whose material was **cloned and colour-neutralised at construction** and whose per-
instance colour is written once (`office-cast-batch.ts:161-184`) — so it would render, but
frozen at its build-time colour and opacity, and no test on the branch would catch it. Not a
defect now; a trap with a loaded spring. Filed as **F-3 (low, latent)**.

The pose side of that clone is fine, incidentally: `OfficeCastBatch.sync()` re-reads
`node.matrixWorld` every frame and writes a zero-scale matrix for any part whose visibility
chain is off, so a halo *would* still appear and animate its transform. It is only the
material that is frozen.

**The near-miss.** `/login` appeared to block its main thread for **139 seconds** — one

## S4-7 — correction to section 10: the dev login is **not** origin-locked, the proxy drops a cookie

Section 10 above ("A trap for anyone writing a QA harness: the dev login is origin-locked")
diagnoses sign-in failures on a private port as the backend rejecting a non-allowlisted origin,
and concludes that harnesses must use the shared `vite preview` on 4173 "and accept the risk
that other workers rebuild `frontend/dist` underneath it".

**That diagnosis is wrong, and the workaround is not necessary.** The real cause is a two-line
bug in `.seam-verify/serve.mjs`, and it is worth correcting because the section currently
pushes every future harness onto the one server that is guaranteed to churn mid-run.

The backend answers `/v1/auth/dev` with **200 and two `Set-Cookie` headers**. The proxy
forwards only one. Measured just now against the running backend:

```
direct to 5001:   HTTP/1.1 200 OK
                  Set-Cookie: lsat_session=W1zfE79p...; HttpOnly; Path=/; SameSite=Lax
                  Set-Cookie: lsat_csrf=9exmX0nY...;    Path=/; SameSite=Lax

via serve.mjs:    HTTP/1.1 200 OK
                  set-cookie: lsat_csrf=oURCYvjn...;    Path=/; SameSite=Lax     <- session gone
```

The cause is `serve.mjs:42`:

```js
upstream.headers.forEach((v, k) => { if (!['content-encoding', ...].includes(k)) out[k] = v })
```

`Set-Cookie` is the one header that legitimately repeats, and collapsing the pair into a single
object key keeps only one of them. `lsat_session` — the `HttpOnly` one that actually
authenticates — is the one lost.

**Why it looks like an origin rejection.** Sign-in *appears* to succeed: the login response
body still carries the user, so `storeAuthenticatedUser` populates the query cache and
`navigate(data.user.next_route)` moves to `/cases/<id>`. My own first probe saw exactly that
and reported success. The very next `/v1/me` then 401s, and the app bounces back to `/login`.
A harness that samples the URL a few seconds later sees `/login` and concludes sign-in failed.
The `403` and `[GSI_LOGGER]` in the console are a **different, unrelated thing** — that is
Google Sign-In not being configured for any local origin, and it is present on 4173 and 5173
too. It was not the cause.

**The fix**, verified working, is `getSetCookie()`, which preserves repeated headers:

```js
const cookies = upstream.headers.getSetCookie?.() ?? []
if (cookies.length) out['set-cookie'] = cookies      // an array, not a joined string
```

Fixed copy at **`.qa-tmp/serve2.mjs`**, serving the HEAD build on **4275**. Confirmed:

```
via serve2.mjs:   set-cookie: lsat_session=6VY1iAhq...; HttpOnly; ...
                  set-cookie: lsat_csrf=QqCkI1Yz...; ...
```

`.seam-verify/serve.mjs` itself was **left unmodified** — another worker may be mid-run against
it — but anyone starting a new harness should use the fixed copy and can then serve a private
build instead of contending for 4173.

**What this invalidates.** Any signed-in result produced through `serve.mjs` on 4273/4274 was
run signed-*out*. That includes the empty `attempts: []` in
`.seam-verify/gate-and-submit.json` (preserved as
`.qa-tmp/gate-and-submit.prior-session.json`), which was read as "the gate could not be
driven" and actually means "the harness never got past the login screen". Section 10's own
`.qa-tmp/parity/head-*.json` are junk for the same reason, as it already says — but the reason
is the cookie, not the origin.

## Security findings

Full write-up in `docs/SECURITY.md`. Severity is judged by what an attacker
actually gets, and this app's shape sets the ceiling for most of it: one account
per Google identity, no sharing between accounts, no multiplayer, no public
profile, no leaderboard. An exploit that only lets a student cheat their own
single-player economy is a product problem; one that reaches a second account is
a security problem. There were none of the latter.

Twenty-six attacks now run in `backend/tests/test_security.py`. Removing the
`user_id` clause from `_owned_session` and disabling the CSRF check makes
exactly four of them fail, which is the evidence that they are not vacuous.

### What was checked and found sound

| area | result |
|---|---|
| CSRF on mutating routes | **sound** — all 30 refuse without a matching token, checked by sweeping `app.url_map` |
| CSRF exempt-list matching | **sound** — exact-path, fails closed on `/v1/auth/dev/`, `/v1/AUTH/DEV`, `//v1/auth/dev` |
| Cross-account access (IDOR) | **sound** — all 16 id-in-path endpoints scope to `g.current_user.id` |
| Account enumeration | **sound** — someone else's real id and an id that never existed return identical 404s |
| Session handling | **sound** — 48-byte tokens, only SHA-256 hashes stored, revoked on sign-out, UTC-forced expiry |
| Prompt injection reaching state | **sound** — see below; the key, not the model, decides correctness |
| Malformed model response | **sound** — six shapes refused rather than half-applied; salvage paths counted and logged |
| Client-awarded economy | **sound** — 9 smuggled fields ignored; the clock is the server's |

### S-1 (medium, fixed) — `SECRET_KEY` fell back to a value published in this repository

`create_app` defaulted it to `"local-only-change-me"` with no warning, so a
production process that forgot to set it booted holding a key anyone can read
here. It signs nothing *today* — sessions are opaque hashed tokens, not Flask's
signed cookie — so nothing is currently forgeable with it; the finding is that
this is a property of the current code rather than a guarantee, and the failure
is silent. `create_app` now raises in production when it is unset or still the
placeholder, exactly as it already did for `DEV_AUTH_ENABLED`. Development is
untouched, and a test covers that too so the guard cannot become a barrier to
cloning the repository.

### S-2 (medium, fixed) — the SPA document and every asset had no security headers

Flask's `after_request` sets four headers, but it only ever sees `/v1/`. nginx
serves `index.html` and `/assets/` straight off disk, so the application page
went out with no `X-Frame-Options` and could be framed by any site, and no
`nosniff`. Fixed in `deploy/ec2/cloudformation.yaml`, which now writes an
include used by the two locations nginx answers itself and adds
`Permissions-Policy` and HSTS as well.

Verified by extracting the config from the template and running nginx 1.24
against it: five headers on the document, on the assets *alongside* their
`Cache-Control`, and on the SPA's 404-to-index fallthrough; `/v1/` unchanged
with exactly one of each rather than a duplicated pair. Both halves matter —
`add_header` in a location silently discards every inherited one, and a
duplicated `X-Frame-Options` is treated as malformed by some browsers.

No Content-Security-Policy yet, on purpose. `docs/SECURITY.md` names the two
blockers: the inline route-hint scripts in `index.html` need hashes or a nonce,
and Google Identity Services needs `script-src`/`frame-src`/`connect-src`
entries enumerated from a real sign-in rather than guessed.

### S-3 (medium, fixed) — `.gitignore` covered `.env` and no other env filename

`backend/.env` was ignored. `backend/.env.production` was **not** — and the
repository tracks `backend/.env.production.example` right beside where it would
sit, so the name is one an operator is actively invited to use, and the real
file holds `TFY_API_KEY` and `GOOGLE_CLIENT_ID`. Given the two databases caught
last night, and that `deploy-sandbox.ps1` runs `git add --all`, this was the same
accident with a different filename. Now `.env.*` is ignored with the tracked
`*.example` templates negated back in; verified both directions.

### S-4 (high **if this stack is promoted to production**, not fixed — infrastructure decision)

`deploy/ec2/cloudformation.yaml` sets `OriginProtocolPolicy: http-only`. The
viewer hop is HTTPS, so a browser never sends the session cookie in the clear.
But CloudFront then forwards that cookie, and every API payload, to the EC2
instance over the public internet unencrypted, and the instance is directly
reachable — `SourceCidr` defaults to `0.0.0.0/0` on port 80 and the stack
outputs the plain-HTTP origin url. An attacker positioned on that path reads
sessions and can serve modified JavaScript to anyone who lands on the origin url.

Not fixed because the fix is a domain plus an ACM certificate on the origin,
which is a decision about the deployment rather than an edit to the template.
The stack calls itself a sandbox and tags itself `ephemeral`; the finding is
that it should not be promoted as it stands.

### S-5 (medium, not fixed — needs a real usage number)

No rate limiting exists anywhere in the backend. The endpoint that costs money
is `POST /v1/attempts/<id>/coaching`: a frontier model at `reasoning_effort:
xhigh`, 5000 tokens, 120 s timeout.

The existing structure bounds it better than it first looks — coaching is
idempotent per attempt (completed returns the saved object, in-flight is refused
for 150 s), and creating an attempt requires answering a question with a
distinct explanation over the minimum length — so the ceiling is about one model
call per question answered, and per account it is bounded by the question bank.
It is a spend risk, not a data risk. A per-account cap on coaching starts is the
right next change, but sizing it needs a real number for what a fast legitimate
student does in ten minutes, and inventing one risks refusing a real student
mid-session. Recommended rather than guessed at.

### S-6 (low, accepted) — prompt injection can inflate a student's own grade

The defences are good and layered: student text is a value inside a JSON object
in the *user* message, never concatenated into the system prompt; both prompts
say it is data; the grade is clamped 0–100; the verdict and error code are
allowlisted; every text field is capped and has angle brackets stripped; a reply
missing a field raises rather than half-applying. Most importantly the model
does not own correctness — `is_correct` is decided against
`question.correct_answer`, and `_validate_coaching` recomputes each choice's
`is_correct` from the same column, so a reply claiming all five are correct
changes nothing.

What remains: `explanation_grade` is a model judgement of the student's own
prose, and it feeds the payout multiplier. A student who talks the model into a
higher grade earns more of their own in-game cash. They cannot change
correctness, reach another account, or extract a key for an unseen question.
Closing it fully means not asking a model to grade prose. Accepted, recorded.

### S-7 (informational) — `start_section` is the one exam verb that does not own its own clock check

`submit_section`, `focus_item` and `record_answer` all call
`enforce_exam_clock` themselves. `start_section` relies on its route calling it
first. Correct today, because that route is the only caller — but it is the one
place where the guarantee sits outside the module that owns it, and a second
caller added later would not inherit it.

untouched, and it is the 3D owner's file. The two assertions were replaced with the
properties the scene actually depends on: the floor never empties and never loses
people as the firm grows, and each layout family's `spread`/`reach` are within (0, 1]
and never take less floor than the family below, which would make an office upgrade
look like a downgrade.

*Evidence:* the command now prints `Office manifest verified: 107 mapped assets
(35 upgrades, 30 staff, 14 connections, 14 rivals, 14 cosmetics), 30 role-assigned
staff stations, 6 reusable floor plans, 15 distinct furnished environments, and 35
visible upgrade states.` and exits 0. Mutation-checked: setting tier 11's
`staffOnShift` to 4 and the campus family's `spread` to .70 makes it fail with
`tier 11 puts fewer staff on the floor than tier 10` and `campus takes less floor than
diplomatic`, so it is checking rather than passing.

Both of these — this and Q-1 — are the same defect wearing different clothes: a
verification command in the README that had quietly gone red, so nobody ran it, so it
stayed red. Both are green now, and the README states the expected output of each so a
future red is recognisable as a regression.

## Q-5 (medium, fixed) — two backend tests only passed from the repository root

`.venv/bin/python -m pytest -q` run from `backend/` failed two tests; run from the
repository root it passed all 404. Both tests did `from backend.app.game import …`,
which resolves only when the repository root is on `sys.path`. Nothing to do with what
they test — `test_the_working_day_streak_counts_finished_cases_not_page_loads` and
`test_a_streak_buys_reputation_standing_but_only_at_the_rate_days_allow` are about
streaks — and the failure mode is `ModuleNotFoundError: No module named 'backend'`,
which reads like a broken environment rather than a broken import.

Both changed to `from app.game import …`, the form every other test in the suite uses.
**404 pass from `backend/` and 404 pass from the repository root**, verified separately.

This was pre-existing: confirmed by stashing this branch's changes and reproducing the
same two failures on the clean tree.

## Q-6 (medium, fixed) — a preload hint was buying `/office` an extra download

`/office` logged `A preload for 'office-three-BX_PiMl0.css' is found, but is not used
because the request credentials mode does not match`. A browser reuses a preload only
when the real request matches it on URL, `as` **and credentials mode**. Vite's
`__vitePreload` sets `crossOrigin=""` on every link it creates; the hints
`vite.config.ts` emits set nothing. So the hint was discarded and the sheet fetched a
second time — an optimisation costing the route a whole extra request.

Counted rather than inferred, with `tools/qa/asset-dupes.mjs`:

| | before | after |
|---|---|---|
| `/office` | `office-three-BX_PiMl0.css` **x2** (5,295 B raw, 1,644 B gzipped) | no asset fetched twice |
| `/map`, `/firm`, `/cases`, `/progress`, `/story` | no asset fetched twice | no asset fetched twice |

Fixed in `frontend/vite.config.ts` by declaring the same anonymous mode on every CSS
hint and every stylesheet that config injects, so they match each other as well as
Vite. Same-origin requests pass the CORS check with no server change, and the entry
`<script type="module" crossorigin>` Vite already emits puts the deployment under the
same requirement, so nothing new is being asked of the origin.

**Ordering re-verified**, because that script's real job is the cascade:
`tools/css-split/nav-order.mjs` reports `0 of 9 routes disagree with themselves`, the
same result the earlier session recorded.

## Q-7 (serious, fixed) — the campaign track had no keyboard route into itself

axe-core, `/story` at 390x844: `scrollable-region-focusable`, one node, `.chapter-track`.
Below 900px the track pans horizontally, and until a chapter unlocks its cards contain
no control to tab to, so a keyboard user could reach its contents only by scrolling
past them. It does not fire at desktop width because the track does not scroll there —
which is why a desktop-only sweep would never have seen it.

`frontend/src/pages/story-page.tsx`: `tabIndex={0} role="group" aria-label="Campaign chapters"`.
One attribute and a name, deliberately the smallest edit that closes it, because this
is the interface owner's file.

`jsx-a11y/no-noninteractive-tabindex` objects to the result. The two checks genuinely
disagree and only axe has a keyboard user behind it, so the rule is disabled on that
one line with the reasoning in place, rather than configured away for the codebase.

## Q-8 (informational, not a defect) — the `/office` 404 was this sandbox, not the app

The first sweep logged a 404 on `/s/archivo/v25/….woff2` and it looked like a missing
font in the build. It is `fonts.gstatic.com` being intermittently unreachable from this
VM. The font tags in `index.html` are absolute and correct, and the CDN returns
absolute `src` URLs to a real Chrome user-agent.

Recorded because the tool's own reporting caused the scare: it printed only the
pathname, so a third-party 404 read as a same-origin one. `sweep.mjs` now names the
host on any failed request that is not the app's own origin.
